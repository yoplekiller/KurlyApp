# Appium CI 자동화 방식 검토 (2026-07-23)

로컬 실기기(WiFi ADB)로만 돌리던 Appium 테스트를 CI에서도 실행하려면, "테스트를 실행할 기기를 어디서 구할 것인가"가 핵심 문제다. 세 가지 방식을 비교했다.

## 비교

| | 1. 에뮬레이터 in CI | 2. 클라우드 디바이스팜 | 3. Self-hosted Runner |
|---|---|---|---|
| 방식 | GitHub Actions 러너 안에서 `reactivecircus/android-emulator-runner`로 AVD(가상기기)를 직접 생성 | BrowserStack / Sauce Labs / AWS Device Farm 등에 Appium capabilities만 원격 연결 | 실기기를 USB로 PC에 연결하고, 그 PC 자체를 GitHub Actions self-hosted runner로 등록 |
| 상시 가동 | O (GitHub 서버, 항상 가능) | O (벤더 서버, 항상 가능) | X (PC + 폰이 켜져 있을 때만) |
| 비용 | 무료 (GitHub Actions 무료 사용량 내) | 유료 (BrowserStack App Automate 월 $199~, AWS Device Farm 기기당 월 $250~) | 무료 |
| 테스트 대상 | 에뮬레이터 (실기기와 미묘한 동작 차이 가능) | 실기기 다수 확보 가능 | 실기기(갤럭시 A23) |
| 이 프로젝트의 걸림돌 | **앱 설치 문제** — 마켓컬리 APK는 제3자 앱이라 공개 레포에 커밋해 배포할 수 없고, 매 실행마다 새로 설치할 합법적 방법이 마땅치 않음 | 가격이 기업용 — 개인 포트폴리오로 상시 유지하기엔 부담 | 없음 — 이미 설치·로그인된 상태의 실기기를 그대로 재사용 |
| 적합한 경우 | 자체 개발 앱(APK 소유권 있음) + 상시 CI가 필요할 때 | 다양한 실기기/OS 조합을 커버해야 하는 회사 프로젝트 | 실기기 1~2대로 개인 포트폴리오/사이드 프로젝트를 데모할 때 |

## 결정: 3번 (Self-hosted Runner)

**이유**
- 마켓컬리는 자체 개발 앱이 아니라 제3자 앱이라, 1번 방식에서 필요한 "매 실행마다 APK를 설치"하는 절차 자체가 저작권상 성립하기 어려움
- 2번은 실기기 확보 측면에서 가장 이상적이지만 개인 포트폴리오가 감당할 가격대가 아님
- 이미 보유한 실기기(갤럭시 A23)를 그대로 활용할 수 있고, 로그인 상태 등 기존 앱 상태를 그대로 재사용 가능

**감수한 트레이드오프**
- "24/7 상시 가동 CI"는 포기 — PC와 폰이 꺼져 있으면 워크플로우가 실행되지 않고 대기 상태로 남음(실패가 아니라 지연)
- 실무에서 self-hosted runner는 보통 "회사 내부망의 특정 디바이스랩에 접근해야 하는" 특수 상황에 쓰는 방식이며, 상시 CI가 필요하면 1번/2번을 선택하는 것이 정공법이라는 점을 인지하고 있음

## 관련 설계

기기 프로필을 여러 개 등록/전환할 수 있는 구조(`src/config/device_profiles.json` + `pytest --device-profile=<이름>`)를 이미 만들어둔 상태라, self-hosted runner 워크플로우도 기존 `galaxy_a23` 프로필을 그대로 사용한다. 나중에 CI에서 에뮬레이터를 추가로 붙이고 싶어지면(1번 방식), 이 구조에 프로필 하나만 추가하면 되므로 확장 경로는 열려 있다.
